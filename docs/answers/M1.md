Q1. What is the difference between an LDAP directory and an Identity Provider?

Plain version: the directory is the register (who exists, their details, their groups). The Identity Provider is the front desk: it checks you are who you claim to be, then gives you a badge that applications accept.
Technical version: LDAP stores identities and can verify a password through a “bind”. It doesn’t issue tokens, keep login sessions, run multi-factor checks or speak OIDC or SAML. Keycloak does all of that and uses LDAP as its source of identities. Apps trust Keycloak’s signed tokens and never talk to LDAP.
In your lab: OpenLDAP holds the 6 users; Keycloak will authenticate them and issue tokens to Co-Note.

Q2. Why should Keycloak use PostgreSQL instead of its development database?

Plain version: the development database is a notebook for testing. You wouldn’t run the school’s front desk from a notebook that can get lost.
Technical version: start-dev uses an embedded database meant for one developer. It isn’t supported for production, doesn’t handle concurrent load or several Keycloak instances, and is hard to back up properly. Postgres gives durability, backups, transactions, and the option to run Keycloak in a cluster. Keycloak’s whole configuration lives in this database: realms, clients, signing keys and sessions.
Evidence: M1-04 (tables in Postgres) and M1-07 (still there after a restart).

Q3. What is the role of an organisational unit (OU) in LDAP?

Plain version: folders in a filing cabinet, for example a “students” drawer and a “teachers” drawer.
Technical version: an OU is a container in the directory tree used to organise entries. It lets you:
point a service at only one part of the tree (a search base);
apply different access rules or policies per branch;
hand management of a branch to a specific person.
An OU is not a group. Membership for access decisions comes from groups (groupOfNames). An entry sits in exactly one OU but can belong to many groups. That’s why your tree has both.

Q4. Why separate identity management from application business logic?

Plain version: every app would otherwise need its own password list, so you’d have ten copies to keep in sync and ten places to lock someone out when they leave.
Technical version: centralising identity gives:
one place to authenticate, enforce MFA, apply password policy and disable accounts;
fewer passwords for users;
apps that never handle passwords at all;
one consistent audit log;
new apps that only need to trust tokens (the “Co-Note Research” challenge in M8).
In your lab: auto-monitor stores its own password hashes today, in AuthController and the users table. M3 removes that responsibility from the app.
